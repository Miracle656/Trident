# Pagination Contract

Issue: [#423](https://github.com/vickydve/Trident/issues/423), generalizing
the opaque cursor introduced for `GET /v1/events` by
[#220](https://github.com/vickydve/Trident/issues/220).

Every list endpoint in the API uses **one** pagination envelope and **one**
cursor implementation (`services/api/cursor`). This document is the contract
those endpoints, and any client, can rely on.

## The envelope

Every paginated list response has the same three fields (the array field's
name is resource-specific — `events`, `contracts`, etc.):

```json
{
  "<items>": [ ... ],
  "has_more": true,
  "next_cursor": "eyJwIjp7InYiOjIsInQiOiJpZDoxMjM0In0sInMiOiJhYmNkIn0"
}
```

| Field | Type | Meaning |
|---|---|---|
| `<items>` | array | The page's rows. Empty array (`[]`), never `null`, when there are none. |
| `has_more` | bool | `true` iff a subsequent page exists. Always present. |
| `next_cursor` | string \| omitted | Present **iff** `has_more` is `true`. Opaque — pass it back verbatim as the `cursor` query parameter to fetch the next page. Never construct or parse this string. |

Request-side, every list endpoint accepts:

- `limit` — page size. Optional; each endpoint documents its own default and
  max. Changing `limit` between calls to the *same* cursor is explicitly
  supported (see "Stability across page-size changes" below).
- `cursor` — the opaque string from a previous response's `next_cursor`.
  Omit for the first page. An empty string is equivalent to omitting it.

An invalid or tampered `cursor` value is rejected with `400
INVALID_ARGUMENT` — it is never silently treated as "first page" or as some
other row (see "Integrity" below).

## Endpoints on this contract

| Endpoint | Keyset column(s) | Notes |
|---|---|---|
| `GET /v1/events` | backend-defined composite key (ledger, tx, event index) | Cursor opaque token is produced by the gRPC indexer backend and re-wrapped by the API via `cursor.Encode`/`cursor.Decode`. |
| `GET /v1/admin/contracts` | `indexed_contracts.id` (UUID, `ORDER BY id ASC`) | Cursor wraps the last-seen `id`; migrated off raw-UUID cursors in #423. |

### Intentionally out of scope

- **`GET /v1/stats/contracts`** — a top-N analytics snapshot ordered by
  `event_count DESC` (a computed, frequently-changing aggregate, not a
  stable row ordering), served from a 60s Redis cache. It has no concept of
  "the next page of this exact ranking" the way a row listing does, and
  paginating a value that can reorder between calls doesn't buy the caller
  the guarantee they'd expect. Left as `limit`-only. Revisit if this
  endpoint grows a genuine drill-down/paging use case.
- **`POST /v1/events/batch`** (`services/api/handlers/batch.go`) — a
  bulk-get-by-ID operation, not a list/scan endpoint; the response contains
  exactly the requested IDs, so there is no "next page" concept.

## Cursor implementation (`services/api/cursor`)

All cursors — regardless of which endpoint issues them — are produced and
consumed by the same package, `services/api/cursor`. An endpoint never
encodes/decodes its own ad-hoc cursor string.

- **Opaque.** The cursor is a base64url string wrapping
  `{"p":{"v":2,"t":"<internal token>"},"s":"<hmac tag>"}`. The internal
  token's shape (a UUID, a composite ledger/tx/event key, a backend-defined
  string, ...) is never exposed to callers and can change per-endpoint or
  over time without breaking the public contract.
- **Integrity-checked.** Every `Encode` computes an HMAC-SHA256 tag over the
  payload, keyed by a server-side secret (`CURSOR_SIGNING_SECRET`, or a
  random per-process key when unset — see `cursor.SetSecret`). Every
  `Decode` recomputes and compares the tag with a constant-time comparison
  before trusting the payload. A cursor that was hand-edited, generated by
  guessing/incrementing an ID, or signed under a rotated-away secret fails
  integrity verification and `Decode` returns an error — the caller gets
  `400 INVALID_ARGUMENT`, never a wrong page of data.
- **Stable across page-size changes.** A cursor encodes only "resume after
  this key", never an offset or page index. Calling the same cursor with a
  different `limit` on the next request resumes at the same logical
  position; it does not skip or duplicate the rows that would have appeared
  under the original `limit`.

## Concurrent-insert semantics

**Forward keyset pagination in this codebase never re-shows or skips a row
relative to the cursor's key ordering, even under concurrent inserts —
*provided* the insert's key does not fall between the previous page's last
key and where the walk has not yet reached.** Concretely, for
`GET /v1/admin/contracts` (`ORDER BY id ASC`, cursor = last-seen `id`):

- A row inserted with `id` **less than or equal to** the cursor's `id`
  (i.e., behind the read position) is invisible to the rest of the walk —
  correct, since the cursor already claims to have delivered everything up
  to that key.
- A row inserted with `id` **greater than** the cursor's `id` (i.e., ahead
  of the read position, including "between" two not-yet-fetched pages) is
  picked up by a later page exactly once, in its correct sorted position —
  it is neither skipped nor duplicated.
- A row is only ever "missed" by a page walk that started *before* the row
  existed and *finished* before the row's key was reached — which is
  indistinguishable from the row simply not existing yet at the time the
  walk observed that portion of the key space. This is the same guarantee
  offset pagination explicitly does **not** provide: offset pagination
  shifts every row's position on each insert, so a walk can skip a row
  entirely (if a row is inserted before the offset) or repeat one (if a row
  is deleted before the offset).
- Rows are never mutated in place in a way that would change their sort key
  (`id` is immutable), so there is no "row moved during the scan" case to
  reason about beyond insertion.

This is verified for `GET /v1/admin/contracts` by
`TestListContracts_ConcurrentInserts_NoDuplicatesNoSkips` in
`services/api/handlers/pagination_integration_test.go`, which pages through
the table while a background goroutine concurrently inserts new rows, and
asserts the collected id set has no duplicates and includes every
pre-existing row.

## SDK auto-paging helpers

- **TypeScript** (`sdk/typescript/src/iterator.ts`): `iterEvents` is an
  async generator that follows `next_cursor` automatically until
  `has_more === false`, with a `maxPages` safety valve. This is the
  reference implementation for the "auto-paging iterator" pattern used
  across this repo's SDKs.
- **Go / Python / Rust SDKs** (`sdk/go`, `sdk/python`, `sdk/rust`): do not
  yet have an equivalent auto-paging helper. Tracked as follow-up work;
  each should expose an iterator/generator over the same envelope
  (`has_more` / `next_cursor`) once a list endpoint they wrap needs one
  beyond `events` (today only the TypeScript SDK exposes an events-listing
  helper at all).
- `GET /v1/admin/contracts` is an internal admin endpoint and is not
  currently wrapped by any SDK, so it has no auto-paging helper to add.
